## 🧠 LeetCode — **1431. Kids With the Greatest Number of Candies** Tags: #Array

Difficulty: Easy

### 💡 **My Intuition**

_Write down your thoughts, ideas, and insights here._

- **Observations:**
    
    1. We have an array of current candy counts and a single integer representing `extraCandies`.
        
    2. For each kid, we need to ask: "If I give this kid all the extra candies, will they have greater than or equal to the person who _currently_ has the most?"
        
    3. Instead of re-calculating who has the most candies on every single turn, we can just find the maximum value in the array once at the very beginning.
        
- **Edge cases:**
    
    - `Multiple maximums`: The problem allows multiple kids to share the "greatest" number of candies, so our condition is strictly `>= max_candies`.
        
- **Expected approach and complexity:**
    
    1. Time: $O(N)$ where $N$ is the number of kids. We need one pass to find the max, and one pass to evaluate each kid. $2N$ simplifies to $O(N)$.
        
    2. Space: $O(N)$ to store the resulting boolean array that we must return.
        

### 🎯 **Concept to learn today: Two-Pass Array Evaluation**

Given an integer array `candies`, where each `candies[i]` represents the number of candies the $i^{th}$ kid has, and an integer `extraCandies`. Return a boolean array `result` where `result[i]` is `true` if, after giving the $i^{th}$ kid all the `extraCandies`, they will have the greatest number of candies among all the kids.

- **The Strategy:** This is a classic "Two-Pass" array problem. The first pass gathers the global context (the current maximum). The second pass uses that global context to evaluate every local element.
    
- **The Flow:**
    
    1. Initialize a variable `max_candies = max(candies)`.
        
    2. Initialize an empty list `result = []`.
        
    3. Loop through each `count` in the `candies` array.
        
    4. If `count + extraCandies >= max_candies`, append `True` to `result`.
        
    5. Else, append `False` to `result`.
        
    6. Return `result`.
        
- **Efficiency:** Traversing the array twice sequentially is mathematically grouped into $O(N)$ time complexity. It relies entirely on simple addition and comparison, making it extremely lightweight on the CPU.
    

## ⚙️ DevOps Essentials — **Docker Basics: Data Volumes & Persistence**

Tags: #DevOps #Docker #Storage #Architecture

Goal: By design, Docker containers are ephemeral. If you deploy a database container, write data to it, and the container crashes or gets deleted, all that data is permanently destroyed. To run stateful applications (like databases or logging servers), you must decouple the data storage from the container lifecycle.

### 🎯 **Quick Review Summary: Bridging the Ephemeral Gap**

Docker provides two primary ways to persist data outside the container.

|**Storage Type**|**Description**|**Best Use Case**|
|---|---|---|
|**Bind Mounts**|Maps a highly specific folder on the host machine (e.g., `/var/log/my_app/`) directly into the container.|**Configuration & Logs.** When you need external automation scripts to easily read logs generated by the container.|
|**Named Volumes**|Docker completely manages the storage location internally on the host disk. You refer to it strictly by a custom name.|**Databases.** Best for PostgreSQL or MySQL data, where you want Docker to handle the permissions securely without worrying about exact host file paths.|

### 💻 **Real-World Code Execution**

Here is how you use a Named Volume in a `docker-compose.yml` file to ensure database records survive a container teardown.

YAML

```
version: '3.8'

services:
  factory_db:
    image: postgres:14
    volumes:
      # Maps the named volume 'pg_data' to the container's internal storage path
      - pg_data:/var/lib/postgresql/data

# You must declare the named volume at the bottom of the file
volumes:
  pg_data:
```

_(If you run `docker-compose down` and then `docker-compose up`, the new database container will reconnect to `pg_data` and all previous records will still exist)._

## 🐧 Linux Learning — Command: **`dmidecode`** (Hardware SMBIOS Data)

Tags: #Linux #Command #dmidecode #Hardware #Diagnostics

Goal: When managing a massive factory floor of bare-metal servers, you often need to audit exactly what physical components are inside a machine without opening the chassis or rebooting into the BIOS. `dmidecode` dumps the motherboard's SMBIOS (System Management BIOS) table directly into your terminal.

### 🎯 **Quick Review Summary: The Hardware Auditor**

|**Scenario**|**Command**|**Description**|
|---|---|---|
|**Get Serial Number**|**`sudo dmidecode -s system-serial-number`**|**The Daily Driver.** Instantly prints the physical Dell/HP chassis serial number. Essential for automated inventory tracking.|
|**Check RAM Specs**|`sudo dmidecode -t memory`|**Burn-in Diagnostics.** Lists every physical RAM slot, showing the exact size, speed (e.g., 3200 MT/s), and manufacturer of the installed sticks.|
|**Check CPU Info**|`sudo dmidecode -t processor`|**Validation.** Verifies the exact physical processor model and core count to ensure it matches the client's requested build sheet.|

## 🏭 Dannie EMS Handbook — **FRU (Field Replaceable Unit) Flashing**

Tags: #EMS #Manufacturing #Hardware #QualityControl

Goal: Understanding how hardware components are electronically tagged on the factory floor, allowing automation tools to accurately read and track them throughout their lifecycle.

### 🎯 **Core Concept: The Electronic Nametag**

A **Field Replaceable Unit (FRU)** is any physical hardware component that a technician can quickly pop out and replace on-site if it breaks (e.g., a Power Supply, a Motherboard, a PCIe Network Card).

To manage this globally, each of these components has a tiny, dedicated EEPROM (Electrically Erasable Programmable Read-Only Memory) chip soldered onto it.

- **The Blank Slate:** When a motherboard is first manufactured, this chip is blank.
    
- **FRU Flashing:** During the early stages of rack integration, an automated script specifically "flashes" (writes) a tiny payload of data into this chip. This data contains the Manufacturer Name, Part Number, and a uniquely generated Serial Number.
    

### 🏢 **Factory Floor Application**

This is the invisible bridge between hardware assembly and software validation. When you run a Linux command like `dmidecode` (as learned above), the OS is actually reading the data that was programmed into those FRU chips.

Before a fully integrated server rack can be shipped, a final automated validation script traverses every node via SSH. It reads the FRU data of the motherboards, RAM, and power supplies, and compares those serial numbers against the official Bill of Materials (BOM) database. If a technician accidentally installed a 16GB RAM stick instead of the required 32GB stick, the FRU read will instantly fail the rack's quality control check.
